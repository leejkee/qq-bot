# QQ Bot V0.2 重构开发计划

状态：待评审。本文将[会话合成讨论](./refactor.md)和[V0.2 技术设计](./qq-bot-v0.2-design.md)整理为可分批实施、可独立验收的任务。文中的限额是评测起点，平台权限和搜索源可用性仍需实测。

## 一、从现有入口切入

| 现有位置 | 当前行为 | 拟改动 |
| --- | --- | --- |
| `src/groups.ts` | SDK 将两类事件映射为同一个 `message.group`。当前在 `dispatchEvent` 按原始类型只放行 @，并裁掉引用等字段 | 在映射前识别事件类型，提取可见字段。保留签名回调、机器人自发消息过滤、被动回复的原消息 ID 和序号 |
| `src/conversation.ts` | `createGroupConversation` 接受一个问题，将可选系统提示和当前问题交给模型 | 新问答入口接收触发消息及冻结的上下文，复用现有模型请求与错误处理 |
| `src/llm.ts`、`src/config.ts` | 已有模型配置、DeepSeek 可选深度搜索和按当前问题链接启用的阅读能力 | 新流程由程序决定是否访问网络，两次模型请求均关闭供应商内置工具，避免一次提问产生两条联网路径 |
| `src/index.ts`、`test/bot.test.mjs` | 启动时装配依赖，现有测试覆盖单轮问答、签名、重投、慢响应和发送失败 | 从装配入口切换流程，以现有 Webhook 测试覆盖新入口，保留旧路径回归直到切换完成 |

首版采用进程内接口和按群隔离的内存缓存。两份草案中的 HTTP 服务、Redis、长期摘要和主动插话均留待后续需求。实现顺序由事件可见性、证据来源和端到端验收决定，无需先迁移目录。

## 二、实施批次与完成条件

### M0　确认平台能力，建立基线

已核对 SDK：项目锁定的 `qq-official-bot@1.2.3` 为两种群消息注册了同一解析器，统一派发为 `message.group`。本项目在 `src/groups.ts` 按原始类型提前过滤了 `GROUP_MESSAGE_CREATE`。腾讯官方 Node.js SDK 的事件分发器也处理两种群消息，保留原始事件类型、mentions 和可选引用索引。本阶段可沿用现有库。[腾讯 SDK 事件分发源码](https://github.com/tencent-connect/qqbot-nodejs/blob/main/src/protocol/gateway/event-dispatcher.ts)

测试全量接收时，特别检查 @ 是否也由 `GROUP_MESSAGE_CREATE` 投递，以及 mentions 中能否可靠识别本机器人。分别覆盖普通发言、@ 他人和 @ 本机器人，确认仅最后一种触发回答。优先观察过滤前的脱敏事件元数据，避免业务层丢弃造成误判。[社区 SDK 群事件说明](https://zhinjs.github.io/qq-official-bot/api/group.html)

用获准的测试群分别发送普通消息、@、引用及附件，记录能否收到、原始事件类型、可用字段以及发送成功回执是否含消息 ID。用脱敏样本回放重复及交叉投递。输出能力表和回放样例；无法观察的字段标记为未知。普通消息不可见时，以可见的 @ 历史、成功发出的回答及能解析的引用为上下文。先在当前版本运行文末三项检查并记录结果。

#### M0 能力表与测试群验证

开发前后均通过 `pnpm typecheck`、`pnpm test`（5 项）和 `pnpm build`。签名回放位于 `test/bot.test.mjs`，使用本地 HTTP 和模拟 QQ 发送回执。

| 场景 | 本地回放结果 | 真实测试群待记录 |
| --- | --- | --- |
| 普通发言、@ 本机器人、@ 他人 | 前台回放中仅至少一项 is_you 严格等于 true 的全量事件触发问答 | 测试群三次均收到 GROUP_MESSAGE_CREATE，mention_is_you 依次为 []、[true]、[false]。三次 ID 比较均未命中。更新代码后待验证真实回复 |
| 同一消息收到全量和 @ 两种事件 | 两种到达顺序及全量重投均只触发一次问答；另一群同 ID 独立触发 | 同一动作是否有两类投递 |
| 引用和附件 | 回放识别到引用结构及附件存在 | 分别发一条引用和附件，记录 reference、scene ext、elements 和附件标志 |
| 成功发送最终回答 | 模拟回执含消息 ID | 此前测试群的 GROUP_AT_MESSAGE_CREATE 实测已收到最终回复成功回执，has_message_id 为 true |

在获准的测试实例设置 `QQBOT_EVENT_PROBE=true` 后启动，按表逐项操作，记录时间和 `qq_group_event_probe`、`qq_reply_receipt_probe` 各字段。观测默认关闭；消息标记仅可在同一进程生命周期内关联。引用相关标志只表明结构存在，引用索引能否还原原消息仍待实测。若未观察到回调，记录测试群设置和已送达的对照 @ 事件。验证结束后关闭开关。

### M1　拆开消息入库与问答触发

适配层产出统一消息，包含群、消息、发送者标识、时间、文本或附件占位、可选引用、是否 @ 和是否来自 Bot。平台标识留在进程内。按群和消息 ID 分别记录“已入库”和“已触发”，避免普通事件先到时吞掉同一消息的 @。在触发点冻结快照后进入群内有界串行队列，群之间共享全局并发限额。沿用当前确认消息与最终回复的序号；仅将成功发送的实质答复或澄清写回上下文，回执缺 ID 时使用内部标识并保留触发关联。

验收：普通消息产生零回复、零模型调用；两种投递顺序各产生一次问答；同群连续 @ 按接收顺序回复，触发后到达的消息不进入旧快照；发送失败的正文不出现在下一轮。

### M2　合成群聊上下文

每群暂按 200 条、60 分钟 TTL 保存消息，清理过期消息及空群。快照暂取最近 50 条以内、历史 4000 Token 以内；用讨论稿中较短的 10 分钟、30 条、1500 Token 窗口作对照。先保留当前问题和可见引用链，再保留提问者近期发言、相关 Bot 回答及其他近期消息，最终按时间排列。引用链限定本群、窗口和预算，遇到缺失或循环即停止。

当前问题单独传入，历史整理为带本地消息编号及群内展示名的记录；缺昵称或重名时分配可区分的别名。用结构化序列化区分记录、昵称和正文，群友文本始终作为用户数据。验收用混杂 MCU 与游戏的群聊回放，检查触发消息只出现一次、引用保留、超限裁剪、同名可区分及跨群隔离。

### M3　分别开发问题理解与检索

两项工作先约定 V0.2 设计第 4 至 6 节的数据契约，可用固定快照和模拟证据分别开发。

| 工作项 | 交付与验收 |
| --- | --- |
| 问题理解 | 第一次请求返回 `QueryDecision`。程序校验分支、长度、查询数量及相关消息 ID 是否属于快照。基础知识走 `answer`，指代不清走 `clarify`，需要查证走 `search`。前两者直接结束模型调用。回放追问、明确要求联网、禁止联网和非法输出，检查决策及独立问题是否保留原约束 |
| 搜索源与证据 | 定义 `SearchProvider → SearchResult[]`，以固定中英文查询比较候选源的原始来源命中、延迟、费用及目标环境可达性，再选首个实现。提供脱离 QQ 的检索 CLI。仅向供应商提交脱敏查询，候选去重排序后提取正文，输出含编号、URL、时间及正文或摘要标记的 `Evidence[]` |
| 抓取边界 | 只接受 HTTP(S)，校验 DNS、实际连接目标和每跳重定向，拒绝内网等保留地址；限制响应大小、时长和跳转次数。用受控样例验证拒绝路径、正文失败回退摘要以及空结果 |

### M4　接通固定问答流程

搜索分支用独立问题、必要上下文和证据生成 `GroundedAnswer`。程序检查正文引用与引用清单一致，且全部属于本次证据，从证据表渲染链接。遇到无证据、超时、非法结构或无效引用，返回说明核验受限的简短回复。搜索不可用时，直接回答和澄清仍可工作。

验收时按请求计数：最多两次模型请求、一轮搜索、三条查询、十个去重候选、三次候选网页正文抓取，证据暂限 8000 Token。总预算另计提示词与输出预留。设置含排队时间的截止时间，队列满时及时提示；日志仅留请求编号、阶段、耗时、调用量与失败原因。以模拟超时、队列饱和和引用越界验证限额及回复行为。

### M5　回归、评测与切换

以固定样例分别评估问题改写、搜索决策、原始来源命中和引用对关键事实的支持程度；记录 Token、平均及 P95 延迟、检索失败率。人工核对“产品规格须有原始来源”“摘要不足以支撑结论”“连续追问能指回上条答复”。先记录基线再议定质量阈值。每批执行 `pnpm typecheck`、`pnpm test` 和 `pnpm build`，集成批另走带签名的 Webhook 回放。

切换前记录旧配置到新配置的映射、系统提示词与规划/生成提示词的分工，以及旧链接阅读行为的覆盖范围。建议在装配入口保留可切回单轮模式的开关；测试两种模式，确认旧配置能启动、新流程禁用隐式联网、切回后可按原方式回答。生产切换另行授权。

## 三、评审时需要落定的事项

| 决策 | 依据与最迟决策点 |
| --- | --- |
| 可展示的群聊范围、成员告知方式及保留期限 | M0 能力表与使用场景；启用普通消息缓存前确认 |
| 搜索供应商及无可用供应商时的启用范围 | M3 检索对照结果；真实联网验收前确认。模拟结果仅用于接口联调 |
| 上下文窗口、并发、队列长度和截止时间 | M2 回放比较及 M4 压测；M5 记录正式参数及质量验收线 |
| 原有深度搜索与链接阅读配置何时退役 | M5 双路径回归与兼容性评审；退役前保留回退入口 |
